# 平台扩展可行性评估

> 评估对象：抖音商城、唯品会、苏宁易购、小红书
> 评估基线：`e:\express`（Android + Compose，包名 `dev.showcode`）
> 评估日期：2026-11-04
> 评估方式：只读代码 + 公开文档/公开页面检索。**没有登录任何平台账号，没有抓取需要登录的私有接口，没有尝试绕过验证码或风控。**
> 结论标注：`[事实]` = 有代码或公开资料直接支撑；`[推断]` = 由架构、公开行为或行业经验推导，未真机验证。

---

## 0. 结论先行

1. **当前账号适配器只适用于「有消费端 Web 订单页 + 能在 WebView 里手动登录」的平台。** 它的数据来源不是平台开放 API，而是官方 H5 自己发出的订单/物流响应（`PddFetcher` / `JdFetcher` 的 `window.name` 钩子），或者官方 H5 的只读页面（`TbFetcher` 的 mtop + SSR 物流页）。
2. **抖音：不建议做，WebView 方案覆盖不了。** 抖音消费端订单入口在 App 内（`我 → 订单`）；公开的 `douyin.com` 网页端没有消费订单中心，官方协议还明确写了付费内容订单「PC 端及网页版暂不支持查询」。Android WebView 里既没有这个页面，也拿不到 App 内嵌 WebView 的登录态。`[事实 + 推断]`
3. **如果一定要扩一家：先做苏宁易购。** 苏宁有公开的 PC 订单管理页、支持账户登录，订单里有运单号、承运商和轨迹；自提件的「收货校验码」走短信，正好可以与本项目现有短信通道互补。工作量 **M**。
4. **唯品会：暂不做。** PC 端订单可查，但官方明确「未开通自提服务」，订单数据里基本没有驿站/取件码，做出来也只会得到「暂无取件码」的卡片，产品价值低；且 PC 登录页以 App 扫码为主，在手机内 WebView 里扫码体验受阻。工作量 **M**，收益低。
5. **小红书：不做。** 网页端不能购物，消费订单只在 App / 微信小程序内；WebView 没有入口。工作量 **L**，且不是当前架构能解决的问题。
6. **更优先的事不是加平台，而是补现有链路。** 淘宝/京东适配器代码已存在，但都还标注「未在真机账号上验证」；抖音这类没有 Web 订单页的平台，更适合靠现有通知监听 / 短信 / 手动导入兜底，而不是硬写一个抓不到的适配器。

## 1. 评估边界

### 1.1 已验证的代码事实

- 账号同步的唯一入口是 `AccountSyncEngine`，按 `Platform` 分派到三家 Fetcher；返回值只有 `FetchOutcome.Success` / `Failure` 两种，且必须区分「成功但零件」与「链路失败」。
- 平台登录统一走 `PlatformLoginScreen` 的官方登录页 WebView，登录成功判据是几条 Cookie key，而不是密码或验证码。
- 账号件的首选身份键是**完整运单号**；既没有运单号也没有码、没有到站阶段、或认不出取件点的件会被 `planAccountSync` 跳过。
- 数据库没有平台专属表：`bound_account` 的 `platform` 是文本列，未知平台在读取时会被 `Platform.of` 静默丢弃，不会让旧版本 App 崩。
- 现有去重只有两条索引：`parcel_dedupe(code, point_key)`（排除空码与 SUFFIX）和 `parcel_tracking_dedupe(tracking_no)`（仅未取件）。新增平台不需要新表、不需要新索引。

### 1.2 本次没有做的事

- 没有在真机上登录抖音 / 唯品会 / 苏宁 / 小红书。
- 没有探测任何需要登录的订单接口、物流接口或下单接口。
- 没有分析平台 App 的私有协议、加固、证书绑定。
- 因此下文所有「能不能拿到」都是**基于公开入口 + 现有架构的可行性判断**，不是抓包结论。

## 2. 适配器契约清单：新增一家平台需要实现什么

| # | 要做的事 | 现有代码参照 | 必须/可选 | 说明与坑 |

| 14 | 演示数据 | `data/DemoData.kt:109-119` | 可选 | 演示模式要覆盖新平台卡片时，才需要加一条内存账号 |
| 15 | 单测 | `app/src/test/java/dev/showcode/core/account/SessionTest.kt:13-69`；`AccountMergeTest`；`TraceParserTest` | 必须（至少第 2 项） | 登录判据和解析规则是纯 JVM 可测的，不要只靠真机点一遍 |

**一句话契约**：新增平台 = 加一个枚举分支 + 一个能返回 `FetchedParcel(trackingNo, stage, pointName, code…)` 的 Fetcher。真正的成本不在 UI，而在「平台有没有可读的 Web 订单页」和「登录态能不能在 WebView 里维持」。

## 4. 抖音专项评估

### 4.1 订单到底在哪些入口能拿到

| 入口 | 是否存在消费订单中心 | 能否被当前 WebView 方案覆盖 | 依据 |
|---|---|---|---|
| **抖音 App 原生** | 有：`我 → 右上角 ≡ → 我的订单`；订单详情里看物流 | **不能**。App 原生页面不是 WebView，钩子无从注入 | 抖音电商学习中心「怎么看抖音购买记录」；多篇公开教程 |
| **`m.douyin.com` / `www.douyin.com` 网页** | 没有消费订单中心。本次实际访问 `www.douyin.com` 只得到内容推荐流；`/shop`、`/mall` 只返回站点页脚，没有商城/订单模块 | **不能**。没有页面可加载，`window.name` 钩子没有订单响应可读 | 本次公开页面访问（2026-11-04） |
| **抖音商城 H5（`haohuo.jinritemai.com`）** | 商品详情/店铺页存在（商家分享商品链接用这个域）；**没有公开的消费端「我的订单」入口** | **不能**。即使存在订单页，也大概率绑定 App 内登录态/设备参数，普通 WebView 读不到 `[推断]` | 抖音电商学习中心商品分享文档；公开搜索结果只出现商品页与店铺页 |
| **抖音小程序** | 小程序运行在抖音 App 容器内 | **不能**。Android WebView 不能承载抖音小程序 | 平台形态决定 |
| **商家侧抖店 / 开放平台** | 抖店开放平台有订单列表、订单详情、物流轨迹、末端服务商推送取件码等 API | **不能用**。这些是**商家**授权后查自己店铺订单，不是消费者查自己买的订单；且需要店铺资质与密钥 | 抖店开放平台文档（订单 API / `logistics/pushpickupcode`） |

**判断**：当前「全尺寸隐藏 WebView + document-start 注入 + `window.name` 钩子 + 订单接口识别」这套方案，核心前提是平台有一个**普通浏览器也能打开、登录后能返回订单 JSON 的 H5 页面**。抖音不满足这个前提，因此**不能覆盖** `[事实 + 推断]`。

补充：网上存在少量教程声称「浏览器登录抖音官网，右上角头像 → 我的订单」。这类内容与抖音官方帮助、官方付费内容协议、以及本次实际访问结果冲突，按低可信来源处理；**不作为可行性依据** `[事实]`。

### 4.2 字段可得性与 UI 降级

前提：以下「App 订单详情可见」是公开资料层面的观察；由于 WebView 拿不到订单，**这些字段在当前方案下的实际可得性全部为「否」**。

| 字段 | App 订单详情（公开资料） | 当前 WebView | 缺失会降级哪块 UI |
|---|---|---|---|
| 运单号 | 可见（订单详情 → 物流信息）`[推断]` | 否 | **最致命**。没有运单号就失去首选身份键：`planAccountSync` 无法按 `tracking_no` 去重/匹配；若同时又没有码，整件会 `Skip(NO_CODE)` 不出卡；若只剩码，卡片还能出现，但归组与去重都变弱。现场模式也会失去「复制单号」出口 |
| 承运商 | 可见 `[推断]` | 否 | 只退化为兜底文案「快递」（`TraceParser.kt:76-78`），不阻断 |
| 取件点 / 驿站名 | 物流中文字迹里通常有「已放至 XX 驿站/快递柜」`[推断]` | 否 | 点名认不出 → 统一落到「驿站未定位」组（`AccountMerge.kt:71-73`）；首页仍能显示，但不能按真实驿站分组 |
| 取件码 / 单号后五位 | 部分场景在 App 物流信息里显示取件码；驿站通常也会发短信 `[推断，低权威来源]` | 否 | 首页卡显示「暂无取件码」；现场模式走空码动作（`NoCodeActions`），但当前动作硬编码「去淘宝查询」，对抖音用户是错误出口，还需要额外改文案/加抖音包名 |
| 商品图 / 标题 | 订单列表可见 `[推断]` | 否 | 首页缩略图与详情页商品卡为空；不影响取件本身 |
| 状态 / 轨迹 | 可见 `[推断]` | 否 | 没有轨迹就无法判定 `AT_STATION` / `DONE`；`planAccountSync` 会把运输中的件 `Skip(NOT_AT_STATION)`，自动标已取也不可能 |
| 店铺 / 下单时间 | 可见 `[推断]` | 否 | 只影响详情页商品信息展示 |

**额外的代码层缺口**：现有状态词表里没有「待收货」这一档（`TraceParser.kt:17-23` 只认「待取件 / 已到驿站 / 已暂存…」）。即便未来拿到抖音订单状态文本，也需要先补映射，否则会落到 `Stage.UNKNOWN` 并被跳过。

### 4.3 登录与风控

- **登录方式**：抖音网页端公开支持手机号 + 短信验证码登录，也支持扫码登录 `[事实]`。登录本身在 WebView 里不是不可完成的事。
- **会话保持**：网页登录后会下发 `sessionid` / `sid_tt` / `uid_tt` 一类 Cookie；具体 key 需要在真机登录后确认，现有代码里没有抖音判据 `[推断]`。
- **但登录态不等于订单权限**：抖音的电商订单中心在 App 内，网页登录态不保证能访问 `haohuo.jinritemai.com` 的订单页；即使能访问，也可能要求 App 内设备标识或额外签名 `[推断]`。
- **风控强度：高** `[推断]`。公开资料显示抖音存在滑块验证、短信二次校验、设备/IP 风险评分。
- **模拟器 / 旧 WebView 是否更容易被拦：是，更容易** `[推断]`。旧内核、模拟器指纹、非标准 UA 都会降低设备可信度，触发二次验证的概率更高；现有实现已在 PDD 上使用桌面 UA 规避「打开 App」页，但抖音的风控不吃同一套。
- **对现有约束的冲突**：本项目明确拒绝无障碍/读屏权限，也不做后台轮询、不保存密码、不绕过验证码。这意味着「读 App 原生订单」的可选路径基本都被排除。

### 4.4 抖音可考虑的替代路径（不是适配器）

1. **通知监听兜底**：`PickupNotificationListener` 已存在。如果抖音 App 会推送「包裹已到驿站 / 请凭取件码取件」类通知，可被现有通道捕获 `[推断]`，不需要新平台适配器。
2. **短信兜底**：驿站/快递员的取件短信本来就会进入现有解析链路；抖音订单本身不是必需数据源。
3. **手动导入**：对少量遗漏件，保留现有「粘贴文本」入口即可。
4. **不建议**：为抖音单独做 App 自动化、无障碍读取、或逆向私有接口。这与项目现有红线冲突，维护成本也不可控。

## 5. 其他平台简评

**一句话结论**

- **唯品会**：订单能读，但没有自提/取件码，暂不做；阻碍是「扫码登录 + 无自提」。
- **苏宁易购**：能读订单、能手动登录、自提码还能由短信补上，是唯一值得先做的；阻碍是「订单页结构待真机确认」。
- **小红书**：消费订单只在 App，Web 没有入口，不做；阻碍是「无 Web 订单页」。

### 5.1 唯品会

- **能拿到的**：PC 端「我的交易 → 订单管理」有订单；官方帮助明确可查配送物流与运单号 `[事实]`。
- **卡点 1：没有自提**。官方帮助写明「唯品会目前未开通自提服务，订单由配送物流直接送到收货地址」`[事实]`。这意味着订单数据里通常没有驿站名、没有取件码；即使适配成功，首页大概率是一张「暂无取件码」的卡，现场模式没有码可出示。
- **卡点 2：登录**。PC 登录页公开提示「打开唯品会 App - 个人中心，扫一扫登录」`[事实]`。在手机内 WebView 里显示二维码、再用同一台手机去扫，是走不通的；若没有账号密码/SMS 登录，登录页这一关就过不去 `[推断]`。
- **结论**：**暂不做**。工作量 M，但核心价值（到站取件码）基本拿不到。

### 5.2 苏宁易购

- **能拿到的**：网站支持用户名/手机号/邮箱/会员卡号登录 `[事实]`；登录后「我的易购」可查订单，配送状态可查 `[事实]`；订单详情应有运单号与物流轨迹 `[推断]`。
- **自提**：苏宁自营自提会向收货人手机发送「收货校验码」（四位数字），作为提货凭证 `[事实]`。这条码走短信，不依赖订单页——正好可以由现有 `SmsReceiver` / 解析链路接住，账号适配器只负责「知道有这单、这单到哪了」。
- **风险**：传统电商账号体系，PC 订单页结构相对稳定；风控强度预计中低 `[推断]`。仍需真机确认订单页是 HTML 还是 JSON、是否需要滑块。
- **结论**：如果业务上确实要扩一家，**苏宁是候选里唯一同时满足「Web 订单可读 + 登录可手动完成 + 有自提码来源」的平台**，工作量 M。

### 5.3 小红书

- **能拿到的**：消费订单在 App / 微信小程序；网页端不能直接购物，订单中心也不在 Web 上 `[事实]`。
- **卡点**：没有消费端 Web 订单页，WebView 方案没有入口；网页登录以扫码为主，手机内扫码不可行 `[推断]`。小红书开放平台的订单 API 面向商家/ISV，不是消费者 `[事实]`。
- **结论**：**不做**。不是工作量问题，是数据入口不存在。

### 5.4 一个值得单独评估的聚合路径：菜鸟

菜鸟隐私指引明确列出「考拉海购、苏宁易购、网易严选、唯品会、聚美优品、蘑菇街、1号店」等平台，用户可在菜鸟 App 内关联登录这些电商账号，由菜鸟汇总包裹信息 `[事实]`。

这给出另一条路：**不做每家电商适配器，而是评估「菜鸟账号」作为一个聚合来源**。优点是可能一次覆盖唯品会/苏宁等多家；缺点是菜鸟自身的登录、H5 结构、取件码展示规则又是另一套适配器工作，且抖音/小红书不在其列 `[推断]`。是否值得做，应在单独立项评估，不应混进本次「平台逐家适配」的结论里。

## 6. 建议的实施顺序与理由

1. **先补现有三家的真机验证，而不是加新平台。**
   - 淘宝、京东代码已写完但源码注释明确未真机验证；拼多多只在模拟器验证过。先把这三家的登录、订单解析、轨迹、失效提示跑通，收益高于新增一家低价值平台。
2. **如果业务坚持扩平台：苏宁易购（M）排第一。**
   - 理由：有公开 PC 订单页；支持账户登录；有运单号/承运商/轨迹；自提校验码可由短信通道补上。它是候选里唯一能同时喂饱「首页卡片 + 现场模式 + 空码动作」三块 UI 的平台。
3. **唯品会（M）排第二，但建议先做需求验证再动手。**
   - 理由：订单可读，但官方未开通自提，取件码/驿站基本缺失；做出来很可能只是「有物流、没码」的卡片。除非用户调研证明唯品会订单占比高，否则不划算。
4. **抖音不做适配器，改用通知/短信兜底。**
   - 理由：消费订单只在 App，WebView 无入口；风控高；做适配器需要换数据来源（App 自动化/无障碍/逆向），与项目红线冲突。若抖音到站通知能进通知监听，就已经覆盖了「提醒」这一核心场景 `[推断]`。
5. **小红书不做。**
   - 理由：网页端没有消费订单入口，不是当前架构能解决的问题。

**一句话顺序**：`补 TB/JD 真机验证 → 苏宁（如必须扩）→ 唯品会（需求验证后）→ 抖音/小红书不做，走兜底`。

### 7.2 推断（必须标注，不能当成结论使用）

- I1. 抖音 WebView 无法覆盖：没有公开消费端 Web 订单页；即使存在也可能绑定 App 登录态/设备参数。**未真机验证。**
- I2. 抖音订单详情里的运单号、承运商、轨迹、商品、取件码可见。依据是第三方教程与常识，权威性低。
- I3. 抖音网页登录后的 Cookie key（`sessionid` / `sid_tt` / `uid_tt` 一类）与登录判据。**未真机登录确认。**
- I4. 抖音风控为「高」：滑块、短信二次校验、设备/IP 评分、模拟器/旧 WebView 更易触发。依据是公开经验文章与行业常识，不是平台文档。
- I5. 唯品会「手机内 WebView 扫码登录不可行」「账号密码登录可能可用」两点均未真机验证。
- I6. 苏宁订单页可被 WebView 读成稳定 HTML/JSON；订单详情含运单号与轨迹。**未真机验证。**
- I7. 苏宁风控「中低」、唯品会「中」、小红书「高」这三档均为经验判断。
- I8. 抖音到站/取件通知可被现有 `PickupNotificationListener` 捕获。取决于抖音是否推送、推送文案是否包含取件码/单号。
- I9. 「菜鸟可作为聚合来源」只是可能性；菜鸟登录、页面结构、取件码规则均未评估。
- I10. 所有 S/M/L 工作量都是相对代码改动量的估计，不是工期承诺。

## 8. 如果要继续验证，最小复测清单

### 抖音（只在决定「不做」之前做一次，用来钉死结论）

1. 真机（非模拟器）用 `PlatformLoginScreen` 打开 `https://www.douyin.com`，走手机号验证码登录，记录是否出现滑块/短信二次验证。
2. 登录后依次尝试公开入口：个人页、`/shop`、`/mall`，确认是否存在消费订单列表。
3. 若任何页面出现订单 DOM，记录订单号、运单号、承运商、取件点、取件码、状态文案样例；没有就停止，不再投入。
4. 记录网页 Cookie key（只记 key 名，不记值），用于判断能否写 `Session.has`。

### 苏宁（如果决定做）

1. 真机 WebView 打开 `mpassport.suning.com`，确认账户登录可用、是否弹滑块。
2. 登录后打开「我的易购」订单页，记录列表是 HTML 还是 XHR，是否含订单号、运单号、轨迹。
3. 找一笔自提订单，确认「收货校验码」确实只走短信，订单页是否也显示。
4. 用现有 `TraceParser` 跑一遍轨迹文本，确认状态词、驿站名、取件码能解析。

### 唯品会（如果决定做）

1. 确认真机 WebView 里是否有账号密码/SMS 登录入口，而不是只能扫码。
2. 确认订单页是否给出运单号与完整轨迹。
3. 确认是否存在任何驿站/自提场景；如果始终没有取件码，直接放弃。
